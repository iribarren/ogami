## Objective

Roadmap feature 19 (milestone M5). The owner manages users in Admin: lists them, invites by email (Mailpit in dev), sets roles, disables and enables accounts, and sends password reset links. Anyone can ask for a password reset from the login page. Admin calls Identity & Access application services ([ADR 0034](../../docs/adr/0034-admin-user-management.md), ADR 0006, context map).

Out of scope:

- public registration (invite-only);
- deleting accounts, changing emails;
- app settings;
- email verification beyond the invitation link;
- async mail transport (mail is sent synchronously after commit).

## Problem and why

- An account exists only through the console (`app:user:create`), and nothing can change a user: roles, password or access. The owner's Admin area is a placeholder.
- `identity-auth` deferred registration, user management and password reset to this feature.

## Model summary (today)

- **User** (`backend/src/Identity/Domain/User.php`): `final readonly`, only `register()`; fields id, email, passwordHash, roles (list of `Role`). Value objects `Email` (trimmed, lowercased), `UserId`; `Role` enum `SOLO_PLAYER`/`GAME_MANAGER`/`OWNER`, no hierarchy.
- **Port** `UserRepository`: `save`, `ofId`, `ofEmail` only (no listing). Doctrine table `identity_user` (id guid, email unique, password_hash, roles json), XML mapping `Infrastructure/Persistence/Doctrine/Mapping/User.orm.xml`. `save` flushes and maps the unique violation to `EmailAlreadyInUse` (known follow-up: the EntityManager is closed afterwards).
- **Application:** `CreateUser`/`GetUser` + handlers, `UserView` (id, email, roles), ports `PasswordHasher` (hash only), `UserIdGenerator`, `AuthenticatedUser`. The command bus wraps each command in a Doctrine transaction. Every other context has its own `Clock` port (`Play/Application/Clock.php`, `Studio/Application/Clock.php`); Identity has none yet.
- **Security** (`config/packages/security.yaml`): session cookie, `json_login` with `login_throttling` (5/min, `NormalizedLoginRateLimiter`), `IdentityUserProvider::refreshUser` reloads the user by id on every request, `SecurityUser` (roles → `ROLE_*`; no `EquatableInterface`, so a changed hash or roles ends the session), no UserChecker. `access_control` has no `/api/admin` rule.
- **HTTP:** `AuthController` (`/api/auth/login|logout|me`). No Admin backend (`backend/src/Admin/` does not exist, but PHPat already lists it and lets it use only `Identity\Application`).
- **Mail:** none. `MAILER_DSN=smtp://mailpit:1025` is set on the php service in `compose.yaml`; `symfony/mailer` is not installed. `symfony/rate-limiter` and `symfony/uid` are installed.
- **Frontend:** `/admin` route guarded by `requireRole('OWNER')`, placeholder `AdminHomePage`. `LoginPage`, `shared/auth/` (`useCurrentUser`, `requireRole`, `safeRedirect`). UI kit: badge, button, card, dialog, input, label, native-select, segmented-control…; no table, checkbox or form library.
- **Tests:** Behat suite `identity` on in-memory fakes (`tests/Support/Identity/`), API tests with `WebTestCase` and a per-file `signIn()`. `make e2e-seed` creates a player and a game manager, no owner. Each e2e spec copies its own `signIn`.

## Decisions

| Question | Decision |
|---|---|
| Sign-up (user, 2026-10-18) | **Invite-only.** No public registration; the console stays for the first owner |
| Reset (user, 2026-10-18) | **Self-service + owner.** "Forgot password" on the login page, and the owner can send a reset link from the user list |
| Removal (user, 2026-10-18) | **Disable only.** No delete; a disabled user's content stays |
| User lifecycle (Claude) | `User` stops being readonly. New fields `status` (`UserStatus` enum `active`/`disabled`) and `createdAt`. Methods `changeRoles(list<Role>)` (at least one, de-duplicated, `UserMustHaveARole`), `disable()`, `enable()` (idempotent), `changePassword(string $hash)` (non-empty). Migration adds `status` (default `active`) and `created_at` (existing rows get the migration time); legacy rows read as active |
| Own account (Claude) | `ChangeUserRoles` and `DisableUser` take the acting user's id. The owner cannot disable themselves or remove their own `OWNER` role: `OwnAccountProtected` (409). That keeps at least one active owner |
| Last active owner (Claude, slice 1 review) | Two owners can disable or demote each other at the same time. `DisableUser` and `ChangeUserRoles`, when the target is an active owner losing that standing, lock every user row (`SELECT … FOR UPDATE`, ordered by id, refreshing managed entities; the table is small) through `UserRepository::activeOwnersForUpdate()` and refuse with `LastActiveOwner` (409) when the target is the only active owner left |
| Disabled sign-in (Claude) | An Identity `UserChecker` refuses a disabled user after the password check (`checkPostAuth`) with the same generic 401 as bad credentials. `IdentityUserProvider::refreshUser` treats a disabled user as gone, so the session ends on the next request |
| User queries (Claude) | `UserRepository::all()` (ordered by email). `ListUsers` returns `UserView` gaining `status` and `createdAt`. `GET /api/auth/me` is unchanged |
| Invitation (Claude) | Aggregate `Invitation` in Identity: id, email, roles, tokenHash, invitedBy (UserId), createdAt, expiresAt (createdAt + 7 days), status `pending`/`accepted`/`revoked`. Commands `InviteUser {email, roles, invitedBy}` (refuses an email with an account: `EmailAlreadyInUse` 409; with a pending, unexpired invitation: `InvitationAlreadyPending` 409; an expired pending one is replaced), `ResendInvitation` (new token and expiry; only pending, else `InvitationNotFound` 404), `RevokeInvitation` (pending → revoked; else 404), `AcceptInvitation {token, password}` (creates the active user with the roles, marks accepted, all in one transaction). Queries `ListInvitations` (pending, with `expired` flag), `LookupInvitation {token}` (email, roles, expiresAt) |
| Password reset (Claude) | Aggregate `PasswordReset`: id, userId, tokenHash, createdAt, expiresAt (1 hour), usedAt. `RequestPasswordReset {email}` (self-service; unknown or disabled email does nothing, silently), `SendPasswordReset {userId}` (owner; 404 unknown, `UserDisabled` 409). A new reset deletes the user's older ones. `ResetPassword {token, password}` changes the hash, marks it used, deletes the user's other resets; refused for a disabled user |
| Tokens (Claude) | Port `TokenGenerator` (Application) returns 32 random bytes as base64url; only `sha256` hex of the token is stored (unique index). Lookup is by hash. Unknown, expired, used, accepted or revoked → `InvalidAccountLink` (one generic error, 422 "This link is invalid or has expired") |
| Password policy (Claude) | Through a link: 8–4,096 characters, else `WeakPassword` (422). `app:user:create` keeps its current rule |
| Mail (Claude) | Install `symfony/mailer` only (no Twig). Identity Application port `AccountMailer` (`sendInvitation(email, link, roles, expiresAt)`, `sendPasswordReset(email, link, expiresAt)`); Infrastructure adapter builds `Symfony\Component\Mime\Email` text + inline HTML. Links use env `APP_PUBLIC_URL` (default `http://localhost:8080`): `/accept-invitation#token=…`, `/reset-password#token=…`. Mail is sent after the command's transaction commits (handler dispatches a mail message with `DispatchAfterCurrentBusStamp`, or equivalent). A transport failure answers 503 `MailUnavailable`; the invitation or reset stays |
| Clock (Claude) | Identity gets its own `Clock` port and adapter, like Play and Studio |
| Timestamps (Claude, slice 1 review) | `identity_user.created_at` stays a naive UTC column (UTC `SystemClock`, display only, same as Studio). New Identity tables (`Invitation`, `PasswordReset`) use `datetimetz_immutable`, so expiry comparisons never depend on the PHP or database time zone |
| After-commit mail (Claude) | Application stays framework-free: handlers call the `AccountMailer` port. Its Infrastructure adapter dispatches an Infrastructure `SendAccountMail` message on `command.bus` with `DispatchAfterCurrentBusStamp`, so the outer command's `doctrine_transaction` commits first; the message handler sends through Symfony Mailer. A transport failure surfaces from `MessengerCommandBus` (unwrapping `DelayedMessageHandlingException`) as `MailUnavailable`; the stored invitation stays |
| Invitation lifecycle (Claude, slice 3) | A partial unique index keeps one pending invitation per email; `InvitationRepository::save` flushes and maps that violation to `InvitationAlreadyPending`, so `InviteUser` revokes an expired pending invitation and saves it before saving the new one. `ResendInvitation` replaces the token hash and sets `expiresAt` to now + 7 days; `createdAt` stays. `AcceptInvitation` checks the password policy first, then the link (`InvalidAccountLink` for unknown, accepted, revoked or expired), then refuses with `EmailAlreadyInUse` when an account was created for the email meanwhile. `ListInvitations` returns pending invitations ordered by email. A stored role that `Role` does not know (user or invitation) is a domain error, not `ValueError`. When several after-commit messages fail, the first surfaces and the others are logged |
| Slice 3 review fixes (Claude, slice 4) | `AcceptInvitation`, `ResendInvitation` and `RevokeInvitation` load the invitation with a row lock (`InvitationRepository::ofIdForUpdate` / `ofTokenHashForUpdate`, `SELECT … FOR UPDATE`, refreshing a managed entity), so an accept and a revoke cannot both win. `InvitationLoader::usableForToken` takes the handler's `now`, so the clock is read once and an invitation expiring mid-command is `InvalidAccountLink`, never `InvitationExpired`. The pending-email index migration first revokes every pending invitation but the newest per email. A concurrent insert of the same invitation id surfaces as `InvitationIdAlreadyInUse` |
| Password reset lifecycle (Claude, slice 4) | `RequestPasswordReset {resetId, email}` and `SendPasswordReset {resetId, userId}`: the caller picks the id (like `InviteUser`). A malformed email is `InvalidEmail`; an unknown or disabled account does nothing and sends nothing. The new reset is saved, then the user's other resets are deleted (`PasswordResetRepository::deleteForUserExcept`), then the mail is queued. `ResetPassword {token, password}`: password policy first, then the reset by token with a row lock (`ofTokenHashForUpdate`); unknown, blank, used or expired token, or a disabled or missing user, is `InvalidAccountLink`. It changes the hash, marks the reset used and deletes the user's other resets. Clock read once per command. `identity_password_reset`: `user_id` references `identity_user`, `token_hash` unique, timestamps `datetimetz_immutable_microseconds`, `used_at` nullable |
| Slice 4 review fixes (Claude, slice 5) | `RequestPasswordResetHandler` refuses a reused reset id (`PasswordResetIdAlreadyInUse`) before it looks up the account, so a reused id never tells whether the email has one; the public endpoint generates the id server-side anyway. Behat checks the unknown and the disabled account in separate scenarios |
| Self-service mail failure (Claude, slice 5) | `POST /api/auth/password-reset-requests` answers 202 even when the mail transport fails (`MailUnavailable` is logged as a warning, never shown), because a 503 only for existing accounts would reveal which emails have one. The reset stays; asking again sends a new link. Owner-sent resets and invitations still answer 503 |
| Rate limits (Claude) | `RequestPasswordReset` endpoint: limiters `password_reset_email_ip` (3 per 15 minutes per normalized email and client IP; user, slice 6: an email-only key let anyone use up a victim's quota) and `password_reset_ip` (10 per hour per IP) in `framework.rate_limiter`; over the limit still answers 202 and sends nothing. Token endpoints need no limiter (256-bit tokens) |
| Reset mail flood (user, slice 7) | **Accepted risk.** The email + IP key lets someone rotating IPs send many reset mails to one address; no email-only cap, since it would let anyone block a victim's resets. Recorded in ADR 0034 |
| Invite mail failure (Claude, slice 7) | A 503 on `POST /api/admin/invitations` keeps the pending invitation without returning its id; the UI refreshes the list and tells the owner to use Resend. OpenAPI keeps the fixed 7 days / 1 hour wording (policy constants, not configuration) |
| Reset timing (user, slice 6) | **Accepted risk.** The self-service reset mails in-request only for existing accounts, so response time can tell whether an email has one. Recorded in ADR 0034; revisit when an async mail transport lands (out of scope) |
| Public API (Claude) | Identity `PublicAccountController` (public in `access_control`): `POST /api/auth/password-reset-requests {email}` → 202; `POST /api/auth/password-resets {token, password}` → 204; `POST /api/auth/invitations/lookup {token}` → 200 `{email, roles, expiresAt}`; `POST /api/auth/invitations/accept {token, password}` → 204. The SPA then signs in with the email and password (accept) or shows the login page (reset). 400/415/422 follow the existing error shape |
| Admin API (Claude) | New `backend/src/Admin/Infrastructure/Http/` controllers dispatching Identity commands and queries; `access_control` `^/api/admin` → `ROLE_OWNER`. `GET /api/admin/users`; `PUT /api/admin/users/{id}/roles {roles}`; `POST /api/admin/users/{id}/disable`, `/enable`; `POST /api/admin/users/{id}/password-reset` → 202; `GET /api/admin/invitations`; `POST /api/admin/invitations {email, roles}` → 201; `POST /api/admin/invitations/{id}/resend`; `DELETE /api/admin/invitations/{id}`. 404 unknown user/invitation, 409 `OwnAccountProtected`/`EmailAlreadyInUse`/`InvitationAlreadyPending`/`UserDisabled`, 422 unknown role or no role, 503 mail. No optimistic lock: user rows are tiny and last write wins |
| Frontend (Claude) | `/admin` becomes the Users page: users table (email, role badges, status, created), Edit roles dialog (three checkboxes), Disable/Enable with confirm, Send reset link; the owner's own row has no Disable and a locked `OWNER`. Invitations section: pending list (email, roles, expires, expired badge), Invite dialog (email + roles), Resend, Revoke. Public routes `/forgot-password` (linked from the login page), `/reset-password` (success state with a link to sign in), `/accept-invitation` (signs in as the new user) read the token from the fragment. Add the shadcn checkbox (radix is already a dependency) |
| e2e (Claude) | `make e2e-seed` adds an owner. A Mailpit API helper (from the playwright container) reads the latest email to an address. Scenarios: invite → accept → sign in; disable → sign-in refused; forgot password → reset → sign in |

## Design

### Backend (slices 1–6)

- Slice 1: user lifecycle (status, roles, password, createdAt), migration, `all()`, `UserChecker`, provider refresh, `ListUsers`, `ChangeUserRoles`, `DisableUser`, `EnableUser`, Identity `Clock`; Behat scenarios.
- Slice 2: slice 1 review fixes (last-active-owner guard); mailer install and port, `TokenGenerator`, `APP_PUBLIC_URL`, after-commit mail; `Invitation` aggregate and persistence.
- Slice 3: slice 2 review fixes; `InviteUser`; the rest of the invitation lifecycle (resend, revoke, accept, list, lookup); Behat scenarios.
- Slice 4: `PasswordReset` aggregate and persistence; password reset commands; Behat scenarios.
- Slice 5: rate limiters, the four public `/api/auth/…` endpoints, API tests, `make api`.
- Slice 6: Admin controllers, `^/api/admin` access control, API tests for every status, `make api`.

### Frontend (slices 7–8)

- Slice 7: Admin Users page and Invitations section, hooks, tests, stories.
- Slice 8: public forgot/reset/accept pages, login link, e2e seed owner, Mailpit helper, Playwright scenarios, feature close.

## Constraints

- Domain stays framework-free; Admin uses only `Identity\Application` (PHPat). Admin never imports the `Role` enum: roles cross as strings.
- Tokens never logged, never stored in clear, never in a query string.
- Every new command is all-or-nothing on the command bus transaction; mail goes out only after commit.
- Frontend uses only the generated client; new UI component only the shadcn checkbox (ADR 0004).
